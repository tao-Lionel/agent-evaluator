# eval_bot 待讨论功能池

## 目的

本文档记录暂不立即实现、但值得后续评估的 `eval_bot` 能力。候选项主要来自对
[`zarazhangrui/feishu-claude-code-bridge`](https://github.com/zarazhangrui/feishu-claude-code-bridge)
的调研，并结合 Agent Evaluator 当前飞书评测 Bot 的定位做了取舍。

这些内容不是已承诺路线图。进入实现前，需要先判断：

- 是否能明显改善评测发起、进度反馈、结果复盘体验
- 是否能复用现有 `eval_bot` / `core` 架构，避免把评测系统改成通用远程 Agent 控制台
- 是否有清晰的权限边界、失败恢复和测试方式

## 背景

当前 `eval_bot` 已支持通过飞书 webhook 接收文本消息，经 LLM Dispatcher 识别意图后执行：

- `quick_eval`：异步评测 HTTP Bot
- `query_results`：查询历史评测结果
- `gen_scenarios`：生成测试场景

现有实现更偏“飞书里的评测入口”。`feishu-claude-code-bridge` 更偏“飞书里的本地 CLI Agent 控制台”，它在飞书通信、会话、队列、卡片交互和本地进程桥接方面有不少可借鉴点，但不应整体照搬。

## 候选功能

### 1. 飞书长连接通道

**想法**：在现有 webhook 之外，增加基于飞书/Lark SDK 长连接的 transport，用于本地开发或不方便暴露公网回调地址的部署。

**可能价值**：

- 本机直接启动后即可接收飞书消息，降低 webhook 隧道配置成本
- 对本地试用、个人评测工作流更友好
- 可以更自然地处理重连、心跳和本地进程状态

**风险和待确认**：

- Python 生态是否有足够稳定的长连接 SDK，还是需要引入 Node sidecar
- 是否值得维护 webhook + 长连接两套入口
- 生产部署是否仍以 webhook 为主

### 2. chat/topic 级会话状态

**想法**：为每个飞书会话保存评测上下文，例如最近使用的 `bot_url`、场景集、评估器组合、最近结果路径和运行状态。

**可能价值**：

- 用户可以连续说“用刚才那个 bot 再跑一遍 hard 场景”
- 群聊或话题内的上下文互不干扰
- 可以支持 `/new`、`/status`、`/use-scenarios` 等轻量命令

**风险和待确认**：

- 会话状态存储位置：内存、JSON 文件、SQLite 还是现有 results 元数据
- 状态过期策略和隐私边界
- 群聊 topic/thread 在飞书事件中的字段稳定性

### 3. 每会话队列、并发上限和取消

**想法**：在 `TaskRunner` 之上增加按 chat/topic scope 串行的任务队列。同一 scope 同时只跑一个评测，新消息或新任务进入队列；同时保留全局并发上限。

**可能价值**：

- 避免同一个群里连续触发多个长评测导致结果串线
- 支持 `/stop` 取消当前任务
- 为后续进度卡片和状态查询提供统一任务模型

**风险和待确认**：

- 当前 Orchestrator 和适配器是否都能安全取消
- 取消后如何清理临时报告、HTTP 连接和评测结果
- 队列是否需要持久化以支持服务重启恢复

### 4. 评测进度卡片

**想法**：把“开始文本 + 结束文本”升级为飞书交互卡片或可更新消息。卡片显示当前场景、整体进度、通过率、失败摘要、报告路径，并提供停止、重跑、查看最近结果等操作。

**可能价值**：

- 长评测不再黑盒等待
- 失败信息更适合飞书端快速阅读
- 后续可以把 HTML 报告、JSON 结果和重跑入口聚合到同一张卡片

**风险和待确认**：

- 飞书卡片字段和更新 API 的复杂度
- 消息更新频率需要节流，避免刷屏或触发限制
- 单元测试需要覆盖卡片 payload，而不仅是文本回复

### 5. 权限、群聊和管理员策略

**想法**：增加可配置的 `allowed_users`、`allowed_chats`、`admin_users`，并支持群聊中必须 @bot 才响应。

**可能价值**：

- 降低误触发评测、越权查询结果和刷屏风险
- 区分普通用户命令和管理命令
- 更适合接入真实团队群

**风险和待确认**：

- 飞书事件里 user/chat id 的配置和获取方式要足够易用
- 未授权时是静默丢弃还是提示，需要按场景决定
- 私聊和群聊的权限边界不同，不能简单只按 chat_id 判断

### 6. 附件、引用消息和场景生成

**想法**：支持读取飞书消息里的附件、图片、文件和引用消息，将其作为 `gen_scenarios` 或后续评测配置生成的输入。

**可能价值**：

- 用户可上传接口文档、需求文档、测试数据，让 Bot 生成场景
- 引用历史消息后说“按这个业务生成 10 条测试用例”更自然
- 为后续多模态或文档驱动评测留接口

**风险和待确认**：

- 附件下载权限、文件大小和本地缓存清理
- 文档解析依赖可能扩大项目复杂度
- 需要防止把敏感附件内容写入公开 results 或日志

### 7. 运维命令和诊断信息

**想法**：增加 `/status`、`/stop`、`/logs`、`/doctor` 等命令，用于查看 Bot、队列、最近任务、配置缺失和飞书通信状态。

**可能价值**：

- 评测失败时能快速区分是被测 Bot、LLM、飞书通信还是本地配置问题
- 管理员可以在飞书内完成常见排障
- 方便后续长期运行

**风险和待确认**：

- 日志输出需要脱敏
- `/logs` 等命令应仅管理员可用
- `doctor` 的检查项要保持轻量，避免本身成为慢操作

## 暂不建议照搬的能力

- 直接把飞书接成本地 Claude Code 控制台：这会偏离 Agent Evaluator 的评测定位。
- 默认允许飞书用户触发任意本地 CLI 操作：权限和安全边界过大。
- 一开始就做完整 daemon、账号热切换、多 workspace 管理：当前需求还没有证明这些复杂度值得引入。

## 建议后续评估顺序

1. 权限、群聊 @ 策略和管理员命令
2. 评测状态模型、每会话队列和 `/stop`
3. 评测进度卡片
4. chat/topic 级会话状态
5. 附件/引用消息驱动的场景生成
6. 长连接 transport
7. 更完整的运维诊断能力

## 待确认问题

- `eval_bot` 的主要使用场景是生产群内共享，还是个人本地评测入口？
- 结果查询是否允许所有群成员查看，还是只允许任务发起人和管理员查看？
- 评测任务是否需要可恢复，还是服务重启后允许丢弃运行中任务？
- HTML 报告未来是只返回本地路径，还是需要上传为飞书文件或发布为可访问链接？
- 是否要把飞书通信抽象成 transport，以便 webhook 和长连接共用同一套业务处理逻辑？
